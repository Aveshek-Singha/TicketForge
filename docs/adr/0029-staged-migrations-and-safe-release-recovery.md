# Migrate schemas in stages and preserve acknowledged work during recovery

Status: Accepted. Date: 2026-10-11. Decision: D-029.

Each data owner uses versioned checksummed migrations through one serialized runner with scoped credentials and locking; application replicas validate their supported schema range. Expand structures, migrate through atomic owner-local bridge writes and guarded resumable backfills, validate parity/constraints/capacity, then cut over and contract after rollback and recovery dependencies end. Keep the old representation authoritative while old writers remain. Preserve allocation/quota/financial guards, immutable quote/history meaning, original deadlines, and Outbox/Inbox atomicity; migrations never initiate provider calls. Bound DDL waits, schedule heavy work with verified capacity, and inspect partial concurrent-index failures. Release recovery uses tested compatible application rollback or forward-fix; do not automatically down-migrate applied schemas or restore old live snapshots. Uncommitted transactional DDL can roll back normally. Database restore is separate disaster recovery with writer/provider-dispatch fencing, isolated verification, and allocation/financial/event reconciliation before writes resume. This costs bridge releases, extra storage, migration load, and mixed-version/interruption/restore tests. Exact tooling, budgets, ownership/topology, backups, recovery commands, and broader RPO/RTO remain unresolved.

Scoped follow-up: [D-095](0095-encrypted-pitr-and-business-safe-isolated-restore.md) selects pgBackRest/WAL retention and protected isolated restore with current independent authority. Restored local consistency is insufficient to resume live effects; application rollback remains separate and irreversible history cannot be reset.
